# Æ Orange AI Computer Current Source And Gaps

This page separates what is present in current source, what selected public
evidence demonstrates, what belongs only to the historical deploy ZIP, and what
still needs implementation or independent proof.

## Evidence Classes

| Class | Meaning |
|---|---|
| Current source | Code or configuration is checked into `system/` |
| Public receipt | A tracked artifact records one named observation and boundary |
| Historical package proof | One older ZIP passed the package checks recorded beside it |
| Configured | A route or integration is represented in source, but current execution is not established |
| Gap | A required artifact, integration crossing, target matrix, or acceptance proof is absent |

No lower class silently promotes to a higher class.

## Publicly Supported Results

The selected files under `proof/` support the exact results listed in
`proof/EVIDENCE_LEDGER.md`. The strongest current public statements are about
named lab workloads:

- 10/10 lanes accepted in one recorded two-computer suite;
- 23/23 cases and MRR `0.9058` in one held-out memory benchmark;
- 5/5 answer-and-source-pointer parity cases in one held-out compact-context
  benchmark;
- one harmless, bounded Brain MCP and Hermes filesystem-read delegation;
- named controlled recovery and current-awareness runs;
- two explicitly alpha experiments that are not production promotions.

The public receipts do not establish arbitrary autonomy, general model
superiority, universal context reduction, studio-quality media, current health
on another machine, or a fully green repository.

## Package Gap

The released prerelease ZIP was published before the current `system/` and
Atomic Orange source publication. Its legacy filename is retained only to
identify the exact artifact. The ZIP has a valid recorded hash and extracted
payload lifecycle, but its proof mode prohibited external mutation and did not
launch external runtimes or models.

A current package still needs all of the following as one coherent release:

- a content lock generated from the current source commit;
- an embedded-secret and credential scan;
- archive path, size, count, and hash verification;
- clean extracted planning, apply, readiness, rollback, and preservation proof;
- target-machine runtime and model probes;
- a new report, proof record, SHA-256 sidecar, and release asset;
- an explicit statement of whether Atomic Orange is included.

Until those exist together, the source checkout and historical ZIP must not be
described as the same deliverable.

## Atomic Orange Gap

Current app source is public under `system/ATOMICORANGE`. Tracked engineering
receipts also describe an earlier machine-local Windows executable and installer
from a different source path. Those receipts recorded a hash, an unsigned
signature state, a ten-second process-survival probe, and incomplete focused
build/test attempts. They do not prove the current public app source produces a
signed installer or completes an end-to-end operator workflow.

Public app closure still requires:

- reproducible current-source build and dependency lock verification;
- signed Windows artifacts, or an explicit unsigned-preview policy;
- clean-machine install, uninstall, upgrade, and rollback evidence;
- visible native proof for startup, connection, streaming, cancellation,
  restart restoration, blocked states, and receipt inspection;
- a source-to-artifact hash and provenance chain;
- publication of the actual installer when it is ready.

## Model And Runtime Gaps

Model weights, secrets, and credentials are intentionally absent. A role in a
manifest means policy exists; it does not mean the model is downloadable,
licensed for the operator, installed, resident, routed, or good enough.

Each target still needs hardware discovery, free-space and memory planning,
operator approval, pinned acquisition provenance, local hashes, runtime probes,
quality evaluation, promotion evidence, and rollback.

The historical package and selected lab evidence are Windows-based. Other
operating systems are source-review targets, not claimed-ready products.

## Integration Gaps

- Public MCP proof covers named stdio, authenticated loopback, and one bounded
  delegation path. It does not cover every MCP client or long-running action.
- Hermes evidence covers named read and process actions. Mutation classes,
  multiple children, long jobs, and failure recovery retain separate contracts.
- External services depend on live credentials, licenses, network access, and
  upstream availability that this repository cannot prove in advance.
- Two-computer evidence comes from one Atom Eons topology. One-computer mode and
  arbitrary external hardware need independent matrices.
- Current-awareness evidence covers one bounded research order and no automatic
  candidate promotion.
- Technically decodable media artifacts do not establish human-reviewed studio
  quality.

## Whole-System Gap

The tracked broad-verifier summary reports 227 green test files and one red
operational-audit aggregate out of 228 discovered files. Named green receipts
remain valid within their contracts; whole-system green remains unclaimed.

## Closure Standard

A gap closes only when the exact acceptance contract, artifact, receipt, and
reproduction path are public. A plan, source file, package hash, process start,
HTTP response, or model narrative cannot close a different gate.
